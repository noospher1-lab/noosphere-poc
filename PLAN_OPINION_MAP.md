## 2. Что меняется

**Главный сдвиг.** Сейчас позиция — это группа *доводов*, а человек «в позиции», если писал в неё или нажал «за». В задании позиция — это место, где *стоит человек*, и стоит он явно, записью в журнал. Доводы остаются составом позиции (`position_nodes`), а людей считает только `stance_log`.

Предлагаемая модель (имена в стиле репозитория):

- **`positions`** — расширить существующую таблицу, а не заводить вторую. Добавить `status` (`active` / `merged` / `split`, см. вопрос 3 про `forming`) и `summary`. `headline` оставить, в задании он называется `title`. Так ID не расходятся с голосованием, а экран дерева продолжает работать.
  - Выключить всё, что стирает позиции: `clear_positions`, `delete_position`, `recompute` в текущем виде (инвариант 4). Пересборка превращается в *предложение* слияний и расколов, которое пишется событиями.
- **`position_nodes`** (position_id, node_id, topic_root_id, added_at) — состав позиции M:N по обсуждению. `nodes.position_id` остаётся как устаревшее поле для старого экрана и голосования, в метриках не используется.
- **`position_events`** — только дописывается: create / merge / split / rename / member_add, с полезной нагрузкой «из каких ID во что».
- **`stance_log`** — только дописывается, поля из задания плюс **`source`**: `person` / `merge` / `split_choice` / `backfill`. Без этого поля слияние позиций засчитывалось бы как «переубеждены», см. вопрос 5.
- **`current_stance`** — производная таблица (user, topic) → position, since, `unclarified` (флаг «не уточнил» после раскола). Обновляется в той же транзакции.
- **`exposures`**, **`question_joins`**, **`answer_acceptances`** — как в задании, только дописываются.
- **`node_joins`** (node_id, user_id, created_at) — только дописывается. Нужна маршрутизатору, чтобы «присоединиться к существующему узлу» увеличивало счётчик у любого узла, а не только у вопроса. См. вопрос 6.
- **`node_addenda.kind`** — `note` (по умолчанию) / `error_ack`. Изменение только добавляет поле, «отозвать» не трогаем.
- **`position_stats`**, **`position_stats_daily`** — производные таблицы.
- **`topic_settings`** (topic_root_id → sort, blind_first_answer, K, порог принятия ответа, MIN_POSITIONS) — пока значения не заданы, берутся умолчания из кода.

**Как держать «только дописывается»:** на каждую журнальную таблицу ставится триггер Postgres `BEFORE UPDATE OR DELETE OR TRUNCATE → RAISE`. Тесты проверяют, что запрет срабатывает. `db.wipe()` снимает запрет явно и только для тестовой базы.

**Хэш-цепочка:** предлагаю не заводить отдельную цепочку, а добавить в `events` поля `prev_hash` и `hash`. Каждая журнальная запись и так дублируется событием через `_log`, поэтому цепочка покроет всё сразу. Сериализация через `pg_advisory_xact_lock` внутри `_log`. Будет скрипт проверки цепочки (`python -m app.chain verify`). См. вопрос 2.

**Код:**

- новые функции в `app/db.py`;

## 4. Противоречия и неясности — нужно твоё решение

1. ~~Нет макета~~ — получен 25.09, см. раздел 5.
2. **Хэш-цепочки в коде нет.** Задание говорит о ней как о существующей. Предлагаю цепочку по `events`: одна на весь журнал, сериализация через advisory lock, на пилоте хватит. Есть и второй вопрос: старые события либо остаются без хэша и цепочка начинается с «генезиса» в момент миграции, либо им проставляется хэш задним числом. Второй вариант — это UPDATE журнала. Я за генезис.
3. **Как рождается позиция.** Сейчас каждый довод, который ИИ не отнёс к существующей позиции, сразу становится новой позицией. Для 10 000 человек это сотни позиций, а не 10–20. Задание говорит: позиция появляется, когда вокруг узла складывается устойчивая группа. Предлагаю добавить статус `forming` (кандидат, на карте не виден) и порог перехода в `active`, например «≥ N человек выбрали её в stance_log». Нужно твоё N. Тот же порог задаёт MIN_POSITIONS для холодного старта.
4. **Что делать с нынешними ручками позиций.** `recompute` (удаляет ID), `oppose` (новая позиция на каждое возражение) и `dissent` (позиция на каждого несогласного) противоречат инварианту 4 и модели задания. Предлагаю: `recompute` превращается в «предложить слияния и расколы» без удаления; `oppose` создаёт возражение-узел без позиции; `dissent` снимает довод из состава (событие), а новая позиция появляется только через порог из п.3. Это меняет поведение нынешнего экрана позиций в дереве.
5. **Кто сейчас «в позиции».** На старте `stance_log` пуст, и все будут «без позиции». Варианты: (а) ничего не переносить, каждый выбирает сам; (б) перенести авторов доводов и «за» на позиции записью `source=backfill`; (в) показать каждому один раз «вы, похоже, здесь — подтвердите». Я за (в): ИИ и система не решают за человека. Отдельно: при слиянии людей переносит система (`source=merge`), и такие записи не должны считаться «переубеждены». Подтверди, что понимаем одинаково.
6. **«Присоединиться» у не-вопроса.** В задании есть только `question_joins`, но маршрутизатор предлагает присоединиться к любому похожему узлу. Предлагаю общую `node_joins`, а «у меня тот же вопрос» записывать туда же. Второй вариант — отдельная таблица на каждый вид.
7. **«Согласен» в потоке ответа.** Это новый узел-«за» с текстом или просто реакция? Реакции в метриках не участвуют. Предлагаю: действие «согласен» без текста ставит реакцию, с текстом создаёт узел-support.
